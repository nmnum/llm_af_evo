# Research: real-domain tie-back feasibility

## 1. Pool sizes

**Coatings — `llm_af_evo/shared/ada_coatings_oracle.py`, `DiscreteADACoatingsOracle`**
- Pools all 4 real MacLeod et al. 2022 (ADA, Berlinguette lab) experimental campaigns into one fixed discrete pool.
- **253 real samples total**, 4D inputs (fuel:oxidizer ratio, acac amount, precursor concentration, annealing temperature), 2 objectives (conductivity max, conductance_std min).
- Every query is a real measured value — nearest-neighbour snap against real rows, `_Y_raw` is never a GP prediction. Genuinely real experimental data.

**"mAb" oracle — `excipient_oracle_mo.py`, `MultiObjectiveExcipientOracle` / `DiscreteMOExcipientOracle`**
- **Not real measured data.** It is a tunable synthetic simulator with independently-configurable per-objective noise/difficulty (`tm_noise`, `kd_noise`, `viscosity_noise`, `tm_difficulty`, etc.), explicitly documented in-file as "not a surrogate of the Waibel data itself" (line 113) — i.e. built to *resemble* the shape of a real antibody-formulation campaign (16D categorical excipient encoding, 3 objectives Tm/kD/viscosity) without being fit to or drawn from real lab measurements.
- Discrete pool default size: `n_samples=500` (`make_discrete_oracle(n_samples=500, seed=42)`), stratified over the excipient catalogue (5 amino acids x 4 sugars x 3 surfactants x EDTA flag) then filled to 500.
- So "mAb pool size" = up to however many samples you build it with (default 500), but the objective values in that pool are simulated dose-response draws with injected noise, not real lab measurements. This is an important framing gap versus the ticket's "real domain" language.

## 2. `_queried` / `make_shared_inits` semantics and budget bounds

From `excipient_campaign_mo.py`:
- `run_mo_campaign` (line 928) resets `disc_oracle._queried = set()` at the **start of every single campaign** (per seed/repeat) and registers that campaign's `n_init` points as queried before batching starts. This was a deliberate bug fix (see in-code comment) for cross-seed pool contamination that used to shrink monotonically across a shared-oracle instance's whole run.
- Because `_queried` is reset every campaign, **the binding constraint is `budget <= pool size` for a single campaign**, not `n_campaigns x budget`. Each campaign gets the full, unqueried pool back. `n_campaigns` (repeats) does not compound against pool exhaustion.
- `make_shared_inits` (line 1064) draws `n_init` points per campaign independently via `rng.choice(len(disc_oracle), n_init, replace=False)` — unique **within** a campaign's own init draw, but **with no deduplication across campaigns' init draws** (nothing prevents campaign 3's init points from overlapping campaign 7's). This is confirmed as the existing, already-used harness pattern (not something to newly introduce) — `run_coatings_generalization.py` calls `make_shared_inits(oracle, args.n_campaigns, args.n_init, rng_seed=args.seed)` in exactly this way with defaults `n_campaigns=3` (pilot) / recommended `20` (real run), `budget=40`, `n_init=10`, `batch_size=5`, pool=253.
- Concretely: on the 253-sample coatings pool, `budget=40, n_init=10` (the file's own defaults) leaves budget well under pool size (40 << 253) — safe. Going as high as `budget≈240` would still be technically safe (< 253) but leaves no headroom and is unrealistic for a "short/realistic" budget tie-back anyway. On the 500-sample mAb pool, `budget` up to ~490 is technically safe by the same logic, and `n_campaigns` is unconstrained by pool exhaustion in both cases — the real, already-observed limiting factor for `n_campaigns` is **statistical power**, not the pool: `run_coatings_generalization.py`'s own code explicitly warns that `n_campaigns=3` (its pilot default) gives Wilcoxon "essentially no power" (max two-sided p=0.25 at n=3) and that `n_campaigns=20` is the threshold used for anything conclusive.

## 3. Original thesis diagnosis (`llm_evolved_afs_comprehensive_log.md`)

- **Coatings — mu_sum dominance** (lines 168, 525, 1004-1006, 1016): "any nonzero uncertainty weight (fixed, progress-decaying, or stagnation-boosted) produces the same candidate selections. 7/8 AFs in Run 4 had identical held-out HV. The sigma term doesn't change rankings." The GP's mean prediction is good enough on this domain (near-independent objectives, broad front, 4D) that the uncertainty/sigma term — the exact mechanism front-range normalisation modifies — has almost no marginal effect (~0.3% HV, "the difference between trust_only and everything else," line 523). This is diagnosed as a structural property of the domain, not a budget-dependent one.
- **mAb — noise floor** (lines 179, 403-405, 1016, 1188): CV = 49.7% (coefficient of variation of HV across campaigns) on the mAb aggregation pathway. The doc states directly: "the fitness signal noise-robustness must be fixed BEFORE gamma recalibration — you can't calibrate gamma on a fitness signal that's dominated by noise" and that mAb results were observed *inverted* (worse AFs winning) before this was understood. Elsewhere (line 973-975) a further complication is noted: on mAb, U-NSGA-III's diversity-driven candidate selection does most of the real work, so **AF scoring differences barely matter there either** — a second, independent dominance mechanism on top of the noise floor.
- Both domains are explicitly described in the docs as blocking clean AF-mechanism comparisons for reasons unrelated to budget: coatings because the sigma term structurally doesn't move rankings; mAb because the fitness signal is noise-dominated (and separately, diversity-dominated).

## 4. Assessment: is a short-budget tie-back testable?

**Coatings**: No. Mu_sum dominance is diagnosed as a property of the domain's landscape (GP mean prediction quality, near-independent broad front), not of how much budget has elapsed — 7/8 AFs were rank-equivalent across the *whole* logged campaigns, not just late-campaign. Front-range normalisation only changes behaviour through the sigma term's scale; if sigma essentially never moves candidate rankings on this domain at any point in a campaign, there is no budget window (short or long) where an early-convergence advantage from normalising it could show up. This is the same failure mode that already blocked the original thesis's clean confirmation, and it is structural, so a short-budget attempt does not sidestep it. Additionally, `DiscreteADACoatingsOracle` pool = 253 is genuinely real data, which is the one point in this domain's favour, but it doesn't help if the mechanism under test is inert here.

**mAb**: More promising as a substrate for showing a sigma-driven effect (the docs call it "the better evolution substrate because the fitness signal can actually separate AFs" — sigma term *does* change rankings there), but two things push against a clean short-budget tie-back: (a) it is not real data — it's a tunable synthetic simulator calibrated to resemble a real campaign's noise/dimensionality, so a "tie-back" here would not actually close the loop with real measurements the way the ticket frames it; (b) CV=49.7% noise floor is large relative to the effect sizes already seen in the confirmatory spec's own pilot data (the exploratory scan's budget=40 lead "collapses toward statistical noise by the final batch," 12/20 wins, p=0.15) — and that pilot data is from the *cleaner* tunable synthetic oracle purpose-built for this study, not the noisier legacy mAb simulator. Layering CV~50% noise on top of an already-marginal, budget-shrinking effect makes a clean early/short-budget detection unlikely without a very large `n_campaigns` (>=20, per the harness's own power warning, likely more given the added noise) — a substantial compute/scope commitment for a result the docs already suggest is noise-dominated.

## Recommendation

Rule the real-domain tie-back **out of scope** for the confirmatory spec:
- Coatings is structurally blocked (mu_sum dominance is budget-independent — a documented property of the domain, not an artifact of long campaigns) — no budget range makes this testable.
- mAb is not real data (it's a synthetic simulator resembling a real campaign's characteristics) and carries a CV=49.7% noise floor on top of an effect that the confirmatory spec's own pilot data shows is already budget-fragile even on the clean tunable synthetic oracle — testing it would require a large `n_campaigns` (>=20, likely more) for a result likely to replicate the "inverted/noise-dominated" outcome the original thesis work already documented, not add tie-back value.
- Both failure modes predate and would very likely reproduce inside a short-budget replication attempt; this is the same failure mode that blocked the original thesis confirmation, not a budget-scoping problem that a shorter run fixes.

If a real-domain tie-back is wanted later as a follow-up (not in this spec), mAb at `budget` in the 20-40 range with `n_campaigns>=20` (pool=500 supports this) is the least-bad option, but it should be framed explicitly as "synthetic domain resembling a real antibody campaign," not "real domain," and expectations should be set low given the CV=49.7% noise floor and the mAb-specific U-NSGA-III diversity-dominance finding (line 973-975) that further mutes AF-scoring differences.
